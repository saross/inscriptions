# Prior-art report: FAIR4RS tooling and metadata standards for a Python Bayesian analysis repo (JAMT/Springer)

## Executive summary

FAIR4RS as a field has reached a notable inflection point in mid-2026. The original Chue Hong et al. (2022) principles remain the canonical reference, but the ecosystem built around them has matured substantially in the past twelve months. Two developments are genuinely new since a six-months-ago baseline: (1) the Research Software Alliance's Actionable FAIR4RS Task Force (kicked off December 2024, first draft guidelines expected end-2025, now in circulation) has begun translating the abstract principles into discipline-agnostic checklists; and (2) Zenodo's October 2024 integration with Software Heritage — which now auto-archives deposits and returns a SWHID (SoftWare Hash IDentifier), freshly standardised as ISO/IEC 18670:2025 — creates a dual-identifier model (DOI + SWHID) that is increasingly expected by publishers. The tooling ecosystem (CITATION.cff 1.2.0, CodeMeta 3.1, RO-Crate 1.2 released June 2025, RSQKit from the EVERSE project) is active and improving. Springer Nature's unified code-availability policy (announced February 2024, now rolling out across its full portfolio) directly affects JAMT and makes depositing analysis code in a persistent-identifier repository mandatory for new submissions. AI-use disclosure in methods sections is now standard across most Springer titles and is unambiguous: generative AI used to produce content must be declared; code-generation AI (Copilot, ChatGPT for code) falls within the same disclosure frame.

Note (verifier correction applied): the FAIR4RS 2-year community review was posted November 2024, not March 2025 as originally stated.

## Recommendations

### Use directly

- **CITATION.cff** (candidate 2) with **cffconvert** (candidate 3) for validation. Schema v1.2.0 is stable; cffconvert validates locally and in CI. Create the file at repo root; it feeds both Zenodo metadata and GitHub's "Cite this repository" button automatically.
- **NLeSC Python template** (candidate 15) as a structural reference. It embeds CFF, codemeta, README conventions, CI, and linting in one actively maintained package. Your repo already exists, but audit your layout against its conventions — particularly the `pyproject.toml`, `CONTRIBUTING.md`, `CHANGELOG.md`, and `docs/` stubs.
- **howfairis** CLI + GitHub Action (candidates 7, 8) as a quick five-point compliance check and README badge. Run once now, then add the Action to CI for ongoing monitoring. The PyPI package (last updated 2022) still works; the GitHub Action was updated April 2025.
- **The Turing Way** (candidate 13) for README structure guidance and the code-documentation chapter. Its README checklist and research-compendium section map directly to a Bayesian analysis repo.
- **NLeSC Guide** (candidate 14) for Python-specific conventions: docstrings, testing, structure, CI, licence. Updated continuously.
- **RSQKit / EVERSE** (candidate 10) as a supplement to the above — its task-driven format ("creating a good README", "FAIR research software") aligns well and is current to 2026.
- **Zenodo–GitHub integration with SWH** (candidate 25). Enable the integration, add `.zenodo.json` for supplementary metadata (publisher can't easily be set in CITATION.cff alone), and verify the SWHID appears on the deposit landing page. The dual DOI+SWHID is now best practice and directly addresses Springer's requirement for a permanent identifier.
- **Springer Nature Code Policy** (candidate 24). Comply directly: add a Code Availability Statement to the manuscript, deposit in Zenodo (not just GitHub), apply an OSI-approved licence (MIT is fine), and cite the Zenodo DOI in the references.

### Adapt approach

- **codemeta.json** (candidates 4, 5). Generating a `codemeta.json` alongside `CITATION.cff` is increasingly expected by registries (Software Heritage, Research Software Directory). Use the web-based **codemeta-generator** (candidate 5; AGPL-3.0 for the tool, output is yours) rather than **codemetapy** (candidate 6, GPL-3.0) to avoid licence entanglement. Alternatively, hand-author the JSON using the v3.1 schema — it is not complex for a single-person repo.
- **F-UJI / FAIR-IMPACT metrics** (candidates 9, 28). F-UJI is primarily data-centric and requires running a server; the FAIR-IMPACT extension for software was released 2024 but is still maturing. Useful for a formal FAIR audit if a grant requires it, but disproportionate for a solo analysis repo at publication time. Use howfairis instead for routine checking.
- **RO-Crate** (candidates 11, 12). RO-Crate 1.2 is a stable, mature standard for packaging computational workflows with provenance. For this repo's run-per-stage pipeline, an `ro-crate-metadata.json` at repo root describing the stages and their inputs/outputs would be a genuine FAIR uplift (especially under F3/R1 principles) and is achievable without the full ro-crate-py library. However, this is a nice-to-have rather than a baseline requirement — Springer and JAMT do not (yet) mandate it.
- **OpenSSF Scorecard** (candidate 16). The research-software average of 3.5/10 is sobering, but the tool is security-focused. For a solo analysis repo, the most relevant checks are: branch protection, dependency pinning, licence present, and CI. Your uv-pinned environment addresses dependency pinning. Consider a one-off scan to identify gaps.

### Ignore

- **codemetapy** (candidate 6): GPL-3.0 is a licence mismatch for a MIT-licenced output; avoid as a dependency.
- **zenodraft/metadata-schema-zenodo** (candidate 20): useful for schema validation but last active Feb 2024; Zenodo's own help pages are authoritative and up-to-date.
- **NERC-CEH repo-guidance** (candidate sourced during search): GPL-3.0 licenced, UK-agency specific, low stars; not broadly applicable.
- **rrtools / rcompendium**: R-ecosystem tools; approach is sound (compendium structure) but Python equivalents are better served by NLeSC template and Turing Way guidance.

## Build-vs-adopt verdict

**Adopt** — almost everything needed already exists and is well-maintained. The correct posture is to assemble a small set of standard files and run existing tooling, not to build anything bespoke. Specifically:

1. **Adopt** CITATION.cff (v1.2.0) + cffconvert for citation metadata and validation (candidates 2, 3).
2. **Adopt** Zenodo GitHub integration + `.zenodo.json` for persistent deposition (candidates 24, 25).
3. **Adopt** howfairis GitHub Action for continuous FAIR-badge checking (candidates 7, 8).
4. **Adopt** NLeSC Python Template conventions as a structural audit reference (candidate 15).
5. **Adopt** NumPy docstring style + numpydoc (candidate 19) for function-level documentation — it is the defacto standard for numpy/scipy/pymc codebases.
6. **Author** a `codemeta.json` (v3.1) using the web generator (candidate 5) — 20 minutes, no code.
7. **Adapt** RO-Crate approach for pipeline provenance if time permits: a minimal `ro-crate-metadata.json` describing the staged pipeline is achievable in under an hour using the spec directly (candidate 11).

Nothing here requires building from scratch. The only genuine gap is that actionable, discipline-agnostic FAIR4RS checklists (the ReSA Task Force output, candidate 21) are still in draft. When released they will be the single most useful reference; monitor the ReSA news feed.
